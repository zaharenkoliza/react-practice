# Преподавателю

## Как устроена сдача

`main` — единая стартовая точка. Студенты делают fork публичного репозитория,
создают свою ветку и открывают pull request в `zaharenkoliza/react-practice:main`.
Приглашать каждого в collaborators не требуется.

Решения студентов **не сливаем в main**: иначе следующий студент получит чужое решение,
а независимые работы начнут конфликтовать. Проверенный PR можно закрыть без merge.
История и комментарии сохранятся. Для следующей практики можно использовать новую
стартовую ветку и отдельные PR.

## Где смотреть результат

- Pull requests → конкретный PR → Files changed: изменения студента.
- Commits: ход работы и промежуточные коммиты.
- Checks: результат lint, тестов и сборки.
- Вкладка Conversation: ответы на вопросы из шаблона PR.

После первого запуска Actions добавьте правило защиты `main`: изменения только через
PR, запрет force push и удаления. Разрешения и доступность отдельных настроек зависят
от владельца репозитория и тарифа GitHub. Защита ветки **не настроена локальными файлами**.
Для первого PR внешнего участника GitHub может попросить владельца разрешить запуск
Actions; после просмотра изменений нажмите Approve and run.

Workflow использует `pull_request` с правом `contents: read`, без секретов и без
`pull_request_target`. Запуск происходит при открытии PR и при каждом новом коммите
в его ветке; на push в main запускается только проверка стартовой функциональности.

## Как читать тесты

| Команда | Назначение | Ожидание на старте |
| --- | --- | --- |
| `npm test` | 7 проверок старого поведения | Зелёные |
| `npm run test:practice` | 6 требований новой практики | Красные |
| `npm run test:all` | Обе группы | Красные до выполнения практики |
| `npm run check` | ESLint, старые тесты, сборка | Зелёные |

В PR обе группы проверяются отдельными jobs. На раннем Draft PR красный статус новой
практики ожидаем. Для готовой работы должны проходить обе группы. На `main` новые
требования намеренно ещё не реализованы: это исходник для совместного написания кода.

Тесты проверяют поведение через доступный интерфейс: подписи полей, кнопки, карточки.
Они не проверяют названия файлов или наличие конкретного хука. Контракт интерфейса
указан в PRACTICE_2.md. Студентам не нужно менять тесты для выполнения задания.

## Что проверять вручную

- Страница владеет состоянием экрана; фильтры и список получают props.
- `visibleUsers` вычисляется, а не синхронизируется отдельным состоянием или эффектом.
- Обновления пользователей не мутируют исходные объекты и массив.
- Сортировка не меняет исходный порядок данных.
- Фильтры остаются доступны при пустой выдаче.
- Стили компонентов изолированы через CSS Modules.
- Интерфейс работает на ширине 375 px, поля имеют подписи, виден фокус клавиатуры.
- Студент способен объяснить поток события от карточки к владельцу состояния.
- В PR не удалены проверки и не изменён workflow ради зелёного статуса.

Зелёный CI не оценивает архитектуру и не является защитой от изменения тестов самим
студентом. Это учебная обратная связь, итоговая оценка требует просмотра кода.

## План на 90 минут

1. 0–10: запуск готового проекта, краткое повторение props/state.
2. 10–20: воспроизвести исчезновение фильтра при пустой выдаче.
3. 20–40: выделить UsersPage и UserFilters, упростить UserList.
4. 40–55: ввести select статуса и сортировку, выделить чистую обработку данных.
5. 55–70: показать один CSS Module, остальное оформление дать готовым фрагментом.
6. 70–80: самостоятельная реализация сброса фильтров.
7. 80–90: проверки, PR, обсуждение решений и резерв.

Первые fork и запуск желательно попросить сделать до занятия. На этой паре нет роутера,
API, Context, store и необходимости в useMemo. Не расширяйте данные без учебной задачи.
